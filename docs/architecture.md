# SentinelFlow 架构设计

## 1. 目标与边界

SentinelFlow 是一个面向事件序列的可解释审计框架。首个领域是 API
安全，首个可交付目标是：

> 离线分析结构化 API 请求日志，通过确定性程序提取请求序列、参数分布、
> 身份关系与访问模式，再由 API Security Skill 约束的大语言模型复核候选，
> 识别参数遍历并输出可验证、可拒答、可评测的安全告警。

第一阶段只闭环 `parameter_enumeration`。横向越权、调用序列异常、接口滥用、
请求重放和参数异常保留统一的数据契约与扩展位置，但不作为第一阶段验收条件。

第一阶段不是自主 Agent，不允许模型自由选择工具或直接执行封禁、删除、限流等
处置。系统是一个可控、可重放的审计流水线。

## 2. 设计原则

1. **先建立简单基线，再证明 LLM 的增益。**
2. **精确计算由程序完成，语义判断由 LLM 完成。**
3. **先描述正常行为和不变量，再判断异常。**
4. **每项结论必须能够回溯到原始请求和确定性特征。**
5. **信息不足时允许拒答，不强迫模型生成告警。**
6. **审计器永远不能读取 Ground Truth。**
7. **日志字段是不可信数据，不能成为模型指令。**
8. **数据、配置、规则、Skill、Prompt 和模型必须版本化。**

这些原则综合吸收了日志序列检测、Web API 不变量检测和 LLM 安全分析研究的
共同经验。文献依据见
[相关工作与参考文献](references/related-work.zh-CN.md)。

## 3. 总体流程

```text
原始 JSONL
  |
  v
[1] 输入校验、脱敏与规范化
  |
  v
[2] actor / source / session / resource 上下文关联
  |
  v
[3] 正常性不变量与统计基线
  |
  v
[4] 窗口构造与确定性特征计算
  |
  +----------------------+
  |                      |
  v                      v
[5a] 简单统计基线      [5b] 高召回候选检测
  |                      |
  |                      v
  |                [6] Skill 约束的 LLM 复核
  |                      |
  |                      v
  |                [7] Schema、证据与拒答校验
  |                      |
  +----------+-----------+
             |
             v
       [8] 告警合并与请求映射
             |
             v
       [9] 独立 Ground Truth 评测
```

### 3.1 输入校验、脱敏与规范化

该阶段负责：

- 校验 JSON 类型、必要字段和时间格式；
- 统一时区、HTTP 方法和路径；
- 保存原始行号与不可变请求序号；
- 对请求头、Cookie、令牌和个人信息进行白名单式脱敏；
- 限制字符串、数组和嵌套对象的大小；
- 标记缺失字段、截断字段和乱序事件；
- 将日志值封装为数据，禁止其覆盖系统指令。

规范化不做安全判断，也不能读取标签。

### 3.2 上下文关联

上下文层维护：

- `actor -> source_ip` 的观察关系；
- `sid -> issuing actor + profile/resource`；
- `resource -> owner/delegation/admin scope`；
- 请求与响应、重试、幂等键和业务状态之间的关系；
- 当前窗口之前的必要历史。

“未观察到关系”不等于“关系不存在”。缺少归属或历史时必须显式标记
`unknown`，不能把未知自动解释为恶意。

### 3.3 正常性不变量与统计基线

正常性知识分为两类：

1. **业务不变量**
   - 会话只能由被授权主体使用；
   - 资源访问必须满足 owner、委托或管理员关系；
   - 调用必须满足必要前序状态；
   - 某些参数组合必须保持一致。
2. **经验基线**
   - 每个主体和接口的正常请求速率；
   - 参数基数、变化范围和转移模式；
   - 正常分页、批处理、重试和高峰行为；
   - 状态码、响应大小和请求间隔分布。

业务不变量来自可信配置、接口规范或人工确认。经验基线只能从训练/开发阶段的
可信正常数据构建，不能使用盲测数据。若未来由 LLM 提议不变量，提议必须先在
正常数据上验证并经人工批准，运行时不得动态加入检测规则。

### 3.4 窗口与特征

窗口是候选生成单位，不是默认标签单位。第一阶段至少构造：

- 全局时间窗口；
- `actor + source_ip + path + parameter_name` 窗口；
- 跨窗口历史摘要。

参数遍历特征至少包括：

- 请求数和不同参数值数量；
- 参数范围跨度；
- 相邻递增、递减和固定步长比例；
- 参数熵和变化率；
- 成功、失败和不存在响应分布；
- 其他参数的稳定程度；
- 请求间隔、突发度和持续时间；
- 与主体自身正常基线的偏离程度。

所有统计值由程序计算，LLM 不得从原始窗口自行估算。

### 3.5 候选检测

候选检测以 Recall 为优先目标，可同时使用：

- 可解释阈值；
- 正常性不变量违反；
- 简单统计异常分数；
- 路径、参数和状态组合规则。

候选不是正式告警。候选必须保存触发规则、特征值、阈值、涉及请求和必要的
正常上下文。

### 3.6 LLM 复核

LLM 只接收最小必要上下文：

- 固定系统约束；
- 版本化 API Security Skill；
- 候选和确定性特征；
- 相关原始请求的脱敏投影；
- 可信业务不变量和正常基线摘要；
- 固定 taxonomy 与输出 Schema。

LLM 负责：

- 判断候选是否有足够证据；
- 区分遍历、正常分页、批处理、重试和配置错误；
- 选择可验证证据；
- 给出正常替代解释；
- 输出告警或 `abstain`。

LLM 不负责：

- 重新计算频率和分布；
- 猜测未提供的权限或资源归属；
- 自由创造类别；
- 把日志中的自然语言当成指令；
- 访问 Ground Truth；
- 自动处置。

### 3.7 校验、合并与降级

模型输出必须依次通过：

1. JSON Schema 校验；
2. taxonomy 校验；
3. 请求序号存在性校验；
4. 证据值与程序特征一致性校验；
5. 告警和拒答条件校验；
6. 重叠窗口告警合并。

校验失败可进行有限次数的格式修复重试。若仍失败，记录错误并保留原候选，
不能静默丢弃，也不能用不合法输出生成告警。LLM 不可用时，系统仍应输出简单
基线和候选结果。

## 4. 信任边界

| 数据或组件 | 信任级别 | 处理原则 |
|---|---|---|
| 系统配置、taxonomy、Schema | 可信且版本化 | 只从受控项目文件加载 |
| 人工确认的业务不变量 | 可信且版本化 | 记录来源与生效版本 |
| API 日志字段 | 不可信 | 脱敏、限长、数据边界封装 |
| LLM 输出 | 不可信 | Schema 与证据一致性校验 |
| 经验正常基线 | 条件可信 | 记录数据来源并检查污染 |
| Ground Truth | 仅 Evaluator 可见 | 与审计进程和配置物理隔离 |
| 模型服务 | 外部依赖 | 最小化发送内容，不发送密钥 |

Prompt 中必须明确标记日志数据块的开始和结束，并声明其中出现的命令、角色、
规则或输出格式均为被审计数据。高风险自由文本字段默认不送入模型。

## 5. 组件职责

```text
sentinelflow/core          事件模型、读取、规范化、窗口和上下文
sentinelflow/features      确定性特征与正常基线
sentinelflow/detectors     规则、不变量和统计候选检测
sentinelflow/llm           模型适配、Prompt、缓存和结构化输出
sentinelflow/alerts        证据校验、拒答、合并和请求映射
sentinelflow/evaluation    泄漏检查、指标、消融和报告
domains/api_security      API 领域 Schema、规则、Skill 和示例
```

共享引擎只能依赖通用事件和候选契约。API 的字段语义、正常流程、异常 taxonomy
和证据规则必须保留在 `domains/api_security/`，以支持未来复用到云审计、
金融风控或其他序列异常领域。

## 6. 第一阶段实验

### 6.1 研究问题

> 与简单阈值、简单统计方法和纯 LLM 相比，确定性候选检测与 API Security
> Skill 约束的 LLM 复核，能否在参数遍历检测中降低 FPR，同时保持 Recall，
> 并生成更忠实、完整和可操作的告警解释？

### 6.2 对照组

1. 固定阈值规则；
2. 简单统计异常基线；
3. 纯 LLM 窗口分类；
4. 候选检测 + LLM；
5. 候选检测 + Skill 约束的 LLM。

### 6.3 消融

- 去掉正常性不变量；
- 去掉经验基线；
- 去掉原始请求，仅保留统计特征；
- 去掉 Security Skill；
- 去掉 LLM，仅保留候选检测。

### 6.4 数据要求

数据至少划分为开发集、验证集、盲测集和纯正常集。拆分应优先按攻击场景、
时间段和主体隔离，而不是随机拆分单条请求。正式实验前检查：

- 相同或近似请求窗口是否跨集合；
- 同一生成模板或随机种子是否跨集合；
- Ground Truth 和攻击名称是否出现在输入、文件名或元数据中；
- 正常基线是否混入盲测或攻击样本；
- 标签粒度是否与请求级和场景级指标一致。

困难正常样本至少覆盖合法分页、批量同步、流量高峰、SDK 重试、共享 IP、
管理员或委托访问、参数跳号以及日志缺失。

### 6.5 指标

检测指标：

- 请求级和场景级 Precision、Recall、F1；
- FPR 和 `1 - Precision`，二者分别报告；
- 参数遍历各变体指标和请求级 Micro 指标；
- 重复告警率与拒答率。

跨类别 Macro 指标在 MVP-2 实现多类异常后报告。

解释指标：

- **忠实度**：解释中的数值和事实能否由输入验证；
- **证据覆盖**：是否包含形成判断所需的最低证据；
- **区分度**：是否分析最有可能的正常替代解释；
- **可操作性**：分析员能否据此定位请求和继续调查。

系统指标：

- LLM 调用数、Token、延迟和成本；
- Schema 失败率、重试率和降级率；
- 相同配置重复运行的一致率；
- 模型、Prompt 或 Skill 版本变化后的性能差异。

置信度只用于排序和阈值研究，不直接解释为真实概率。若样本量允许，应报告
分桶准确率或校准误差。

## 7. 可复现性

每次运行生成 Manifest，至少记录：

- 数据集 ID、哈希、拆分策略和随机种子；
- 代码提交版本；
- 配置与阈值；
- taxonomy、不变量、Skill 和 Prompt 版本；
- 模型供应商、模型标识和参数；
- 输入哈希、缓存状态和执行时间；
- 数据截断、脱敏和错误统计。

低 temperature 不能保证完全确定。可复现性必须通过缓存、完整版本记录和重复
运行测量共同保证。

## 8. 扩展路径

完成参数遍历闭环后，按以下顺序扩展：

1. 接口滥用和请求重放：复用时间、频率与指纹特征；
2. 调用序列异常：加入可配置状态机和长程历史；
3. 横向越权：加入权威资源归属与委托关系；
4. 参数异常：加入分群基线和多变量一致性；
5. 调查型 Agent：仅开放只读工具，如扩大窗口、查询会话和资源归属；
6. 实时处理与跨领域复用。

Agent 化必须晚于稳定的工具契约、拒答机制、操作审计和离线评测，不得通过
Agent 自主性替代已有的确定性控制。
